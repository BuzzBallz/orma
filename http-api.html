API reference

The thirteen routes Orma serves, the question each one answers, its parameters, and a real Devnet response.

Orma exposes thirteen GET routes over plain HTTP. The server is src/api.mjs: node:http, no framework, no middleware stack. The default listen address is http://localhost:8787, overridable with PORT.

Every response body on this page was captured from the running service against XRPL Devnet on 2026-09-12, server build 3.4.0-rc5. All of them were taken at ledger 5263343 except the /api/demo/state capture, which is from ledger 5263439 a few minutes later, and the two history routes, captured on 2026-10-13 (server build 3.4.1, ledgers 6091723 and 6091724) once their responses stated the window they cover, and /api/oracle-aggregate, documented that day from ledger 6092503. The Halden Structured Credit IV captures were taken on 2026-10-20 (server build 3.4.1, ledgers 6273933 and 6273934, and 6274019 for its /gate). Responses are trimmed for length where noted, never rewritten.

Warning

This runs on Devnet, not Mainnet. XLS-65 vaults and XLS-66 lending are not amended into Mainnet, so

there is no production deployment to point at. network is hard-coded to "devnet" in

src/api.mjs, and health.source reports where the data came from: "devnet" for live reads,

"fixtures" for the recorded ring.

Rules that bind every response

These are contract-level, not per-route. They are what makes the responses safe to consume.

1. Money is a decimal string in drops

One XRP is $10^{6}$ drops. Every monetary quantity leaves the API as a plain decimal string of drops, never a JSON number.

XRPL NUMBER fields carry up to 19 significant digits and may arrive in scientific notation. A JSON parse into a JS number destroys them silently, and BigInt("1e17") throws outright.

// wrong, both of these
const nav = Number(body.navCorrect)
const assets = parseFloat(body.assetsTotal)

// right
import Decimal from 'decimal.js'
Decimal.set({ precision: 40 })
const assets = new Decimal(body.assetsTotal)   // "51000000" drops

Internally every amount is a Decimal at precision 40, and every serialisation goes through str() in src/num.mjs, which emits toFixed() and therefore never scientific notation. A real captured value that breaks a float: "periodicPayment": "3333346.017258355048".

For chart pixel positions, Number(x) after dividing to a human scale is acceptable. For anything displayed as a figure, it is not.

2. Absent means zero, and the API normalises it away

rippled does not store an optional field (declared SoeDefault) while it holds its type default, so absent means zero. A vault carrying no unrealised loss has no LossUnrealized key at all, not "0". That single behaviour is the root of the finding this whole project is built on, and it is handled in exactly one place: num() in src/num.mjs, which maps undefined, null and "" to zero.

Consumers may rely on presence. Every numeric field in every response below is always emitted, defaulting to "0".

Note

Two deliberate exceptions, both of which use null to mean "not known" rather than "zero".

On broker-history, debtBefore, debtAfter, coverBefore and coverAfter are null, not

"0", when brokerStateKnown is false. An impairment does not touch the LoanBroker object at

all, so that transaction genuinely does not report the book. Emitting "0" would read as an empty

book, which is a different and much worse claim.

On the pledge block of /api/mpt/:mptId/nav and /api/mpt/:mptId/resolve, valueHeld,

valueReported and overstatement are null when the resolved document carries no unitValue,

alongside an unpriced explanation. Same reasoning: an unvaluable pledge is not a pledge worth

zero.

3. Every 200 carries a ledger stamp

serverTime and ledgerIndex are prepended to every successful body by stamp(). GET /api/health is the one body that does not go through stamp(), because it builds the same two fields itself. serverTime is the ledger close time converted from the Ripple epoch (offset 946684800), not the server's wall clock, so two fields read in the same response come from the same ledger.

4. The default list order is worst first, by grade

GET /api/vaults sorts by gradeNumeric ascending. It does not sort by navDivergenceBps.

$$\delta = \operatorname{round}\left( 10^{4}\cdot\frac{\text{NAV}_{\text{naive}} - \text{NAV}_{\text{held}}}{\text{NAV}_{\text{naive}}}\right)$$

Rounded to the nearest basis point, not truncated: bps() in src/num.mjs ends in toFixed(0), which is half-up under decimal.js. The captured divergence of 1961 is $1960.7843\ldots$ rounded, and truncation would report 1960.

Divergence only becomes non-zero once a loss has been declared. A manager sitting on an overdue book who has declared nothing reports $L = 0$, so $\delta = 0$, so a divergence sort puts the most dangerous facility at the bottom of the list. In the live capture below, Kestrel Bridge Financing II sorts first at gradeNumeric: 26 with navDivergenceBps: 0, above Meridian Trade Finance I at gradeNumeric: 89 with navDivergenceBps: 1961. That inversion is the thesis, not a sorting bug: Meridian declared its loss and holds cash against every remaining claim, Kestrel has two distressed loans and reports par.

Every route that answers GET also answers HEAD, with the same status and headers and no body, so a link checker sees the status a reader would.

A vault id must match [A-Fa-f0-9]{64} and an MPT issuance id [A-Fa-f0-9]{48}. Lowercase hex is accepted and upper-cased before lookup. A path that matches no pattern returns {"error":{"code":"NOT_FOUND","message":"No route GET /api/nope","retryable":false}}.

6. CORS, and which three routes are deliberately public

Every GET, HEAD and OPTIONS response carries Access-Control-Allow-Origin: *, Access-Control-Allow-Headers: * and Access-Control-Allow-Methods: GET,HEAD,OPTIONS, so the frontend works from any origin. OPTIONS returns 204. A POST gets none of them, and an operator POST that carries an Origin header, which a browser always sends, is refused 403 before it runs.

The meaningful distinction is caching, and it is opt-in per route. The default is Cache-Control: no-store. Three routes pass { cors: true } and get Cache-Control: public, max-age=4 instead:

  • GET /api/vaults/:vaultId/nav
  • GET /api/mpt/:mptId/nav
  • GET /api/mpt/:mptId/resolve

The first two exist to be called by a party with no relationship to us. That is the entire point of writing a URL into a token: a second broker handed vault shares as collateral holds an MPT issuance id and nothing else, has no access to the facility's reporting, and has no reason to ask us for permission first. Both serve read-only public ledger state, so there is nothing to protect, and max-age=4 matches POLL_MS, the reader's 4000 ms poll interval in src/poll.mjs, so a cache cannot serve a figure older than one reader tick. GET /api/mpt/:mptId/resolve carries the flag as well, because it is the diagnostic a lender runs against those same two routes.

Warning

The metadata that carries the NAV URL is written into the MPTokenIssuance at creation and can

never be rewritten. The contract at the end of those two routes is therefore effectively permanent:

fields may be added, nothing may ever be renamed, retyped or removed.

GET /api/health

Is the reader up, which ledger is it on, and is it currently degraded. No parameters.

ok is false until the first poll tick completes, and again whenever the last pass failed to read a vault. The API starts listening before the reader connects, which is honest rather than pretending to be ready.

curl -s http://localhost:8787/api/health
{
  "ok": true,
  "contractVersion": "1.0.0",
  "source": "devnet",
  "network": "devnet",
  "ledgerIndex": 5263343,
  "serverTime": "2026-09-12T22:20:22Z",
  "buildVersion": "3.4.0-rc5"
}

Two fields appear only while upstream is unhappy: degraded: true and lastLedgerAgeSeconds: <number>. They are additive, and source never flips automatically. On a failed read the reader keeps the last good snapshot rather than blanking, so a consumer should show stale data with an age banner rather than an empty screen.

Each vault row, each vault detail and each orma.nav/1 document carries the age of its own snapshot, which can be behind the envelope's ledgerIndex when that vault's last read failed:

"freshness": { "readAt": "2026-09-12T22:20:22Z", "readLedgerIndex": 5263343, "ageSeconds": 0, "stale": false }

ageSeconds is in ledger time; stale turns true past 30 seconds. In an orma.nav/1 document, asOf and ledgerIndex are the snapshot's own.

buildVersion is reported, never asserted. Devnet moves.

Things in there that are easy to misread:

  • oracle.dimensionsOnChain[].raw is hexadecimal, because AssetPrice on an XLS-47 PriceData

is a UInt64 serialised as hex. c4452 is 803922, which at scale: 6 decodes to 0.803922. Writing "100" into that field means 256, not one hundred. Full detail in /mathematics.

  • oracle.publisher and oracle.oracleDocumentId name the account and document the answering

reader publishes to. This capture is from the deployed reader, rPuYT6SZopnZopp4fmvkfd5eeXQTsozz6H; during the event it was rpVg1…, whose objects stopped updating on 13 September. Document id 5 is Halden. The full mapping is in the quickstart.

  • coverRateMinimum and coverRateLiquidation are in units of $10^{-5}$. A stated 10000 is

$0.10$. Both are divided by $10^{5}$, which is why maxLiquidatableNow is $\lceil 10{,}000{,}000 \times 0.10 \times 0.10 \rceil = 100{,}000$ drops against a coverAvailable of "5000000". strandedCoverFraction: "0.9800" is the 98% of posted cover that cannot be reached at the current book size.

  • canWithdraw is true here because the vault is in Redemption. During the Investment phase it

reads false with withdrawBlockedReason: "tecTOO_SOON", which is not an error. VaultWithdraw returns tecTOO_SOON for the entire Investment phase of a closed-ended vault regardless of liquidity. It is a phase predicate, verified on Devnet with 80 XRP of AssetsAvailable sitting in the vault.

  • impairable: false on an already-impaired loan is correct. A loan may only be impaired once it is

already past due, and only once.

  • score.notchTrace is the entire derivation. No weights are applied anywhere. See

/mathematics.

  • score.dimensions carries six entries, not five. The sixth, HEADLINE, is the composite

itself restated as a row so a table can render it alongside the factors. It is an output, not a measured factor.

Both readings are returned on purpose:

$$\text{NAV}_{\text{naive}} = \frac{A}{S} \qquad \text{NAV}_{\text{held}} = \frac{A - L}{S}$$

Handing over only the honest number asks the consumer to take our word for it. Handing over both, with the gap named in basis points, lets them see what the obvious computation would have told them. provenance names the three ledger fields so they can recompute it without trusting us: $(51{,}000{,}000 - 10{,}000{,}000) / 51{,}000{,}000 = 0.803922$. scale is the vault's Scale: 0 for an XRP or MPT asset, 6 by default for an issued currency, whose vault mints $10^6$ share units per unit of asset. $S$ is then unitsOutstanding divided by $10^{\text{scale}}$.

assessment is labelled advisory: true and can be null. The valuation is a measurement, the grade is an opinion, and the grade failing to compute must never take the valuation down with it.

GET /api/vaults/:vaultId/nav-history

What one unit of this facility was worth after each transaction that changed it: one point per successful transaction that modified the Vault while it had shares outstanding, oldest first.

parameterinrequirednotes
vaultIdpathyes64 hex characters

Each point is read from that transaction's own metadata, not reconstructed: AssetsTotal and LossUnrealized from the Vault node's FinalFields, and the shares from the MPTokenIssuance node when the transaction moved them (between a deposit and a withdrawal the count carries forward). The transactions come from account_tx on the vault's pseudo-account, which lists every transaction that touched the Vault, impairments included, whoever signed it. The response is cached for 15 seconds.

Devnet prunes old ledgers in steps, each server on its own schedule: rippled's online_delete drops everything below the server's previous rotation point at once, and the public endpoint spreads requests over servers whose oldest ledgers differ. account_tx states the range it searched, never what it no longer holds, so a history can come back whole, cut or empty. Every read is therefore merged with the archive in evidence/devnet-tx/: the four facilities' account histories as captured on 13 October 2026, declared per account in its _manifest.json. The two are merged by hash, the live copy winning, and a point whose transaction Devnet no longer returned says "source": "archive". window says what the series rests on:

fieldmeaning
completetrue when no ledger is missing from the vault's creation (fromLedger) to its last change (toLedger: the Vault's PreviousTxnLgrSeq, or the live read's top when that is unknown)
reasonwhy not, when complete is false: the creating transaction was found in neither, or the first ledger that neither range covers
livethe range the live read covers: the one account_tx says it searched (its ledger_index_min and ledger_index_max, which differ between servers), starting instead at the ledger after the oldest transaction returned when the page limit stopped the read, or the span of what it returned when it states no range; then the transactions it returned, and truncated
archivethe capture time, the declared range, the transactions declared for this account, whether all of them loaded (intact), and how many the live read no longer returned (added). null for an account the archive does not cover

truncated is true when the live read stopped at its page limit, 5 pages of 200, with older transactions left.

This is the second lever, measured. Cover liquidated on one default is

$$T(p) = \min\Big(\big\lceil D \cdot c_{\min} \cdot c_{\text{liq}} \big\rceil,\; p,\; C\Big)$$

with $D$ the broker's total book, not the principal of the exposure that defaulted, and $D$ decremented as each default lands. Declaring the largest exposure first therefore consumes the least first-loss capital. In this capture, 30 XRP first then 10 XRP consumed "500000" drops of cover. 10 XRP first then 30 XRP would have consumed "700000". The 200,000 drop difference falls on the unit holders, on identical losses.

bestPossible is best for depositors, meaning the most cover consumed. worstPossible is the least. fairness is the observed consumption placed between them:

$$\phi = \frac{T_{\text{observed}} - T_{\min}}{T_{\max} - T_{\min}}$$

"0.0000" is the investor-worst sequence, "1.0000" the best, and it is defined as "1.0000" when the two extremes coincide. recommendation is the same arithmetic pointed forwards, and is only applicable with two or more distressed loans. Derivation in /mathematics.

Note

LoanManage carries no LoanBrokerID, and an impairment does not touch the LoanBroker object at

all, so a naive filter over account_tx silently drops every impairment. The join that closes it is

Loan.FinalFields.LoanBrokerID in the same transaction metadata. Before that fix every default

looked unsignalled, and the rule written to reward disclosure was penalising it.

window reads as on nav-history, over the owner's history: complete when no ledger is missing from the broker's creation to the later of its own last change and its vault's, since an impairment touches the Vault and the Loan but never the LoanBroker. When it is not complete, the grade is withheld rather than computed: grade, score and observations.defaultsWithoutPriorImpairment are null, withheld is true, the one finding is HISTORY_INCOMPLETE, and ordering is not applicable. Pruning removes the oldest transactions first, and for this broker those are its defaults: graded on what would remain, the same record reads "no defaults declared" and scores A 100 instead of E 25. npm run check:archive replays that case.

Tip

Two failure modes worth knowing about. A pointer that answers HTTP 200 with a document carrying no

unitValue is reported as ok: false with "answered, but the document carries no unitValue", not

as a success. And when a pledge cannot be valued, the pledge block is still returned with null

values plus an unpriced explanation, rather than crashing the caller. Both rules exist because an

early version of the pointer resolved to this diagnostic instead of to the valuation, returned a

perfectly good 200 with no unitValue on it, and took the caller down.

Following the pointer is bounded by a 2500 ms AbortController timeout. It is a URL written by a third party, and it is the only step that leaves the ledger.

The four facilities are baked by the scripts in src/demo/ and their ids are written to demo/*.json, which is how npm start finds them without anyone copying a 64-character hex id by hand while someone is watching.

Operator routes

There is one further family, POST /api/demo/:action, reserved for actions that mutate ledger state during a live demo: impairing a loan, declaring a default, revoking a credential. It is not part of the read API, and it is not documented per action because the action set is supplied by the host rather than fixed by the server: createApi(reader, { demo }) takes a map of action name to handler, and /api/demo/:action dispatches into it.

Note

src/index.mjs does not pass a demo map. In the shipped entrypoint the dispatcher is reachable

but the map is empty, so every POST /api/demo/:action from loopback answers

404 {"error":{"code":"NOT_FOUND","message":"no demo action \"<name>\""}}. Nothing here mutates the

ledger as shipped. The facilities are built by the scripts in src/demo/, which are run from a

terminal and take no key. Treat this family as an extension point, not as an available API.

It is bound to loopback. A request whose remote address is neither 127.0.0.1 nor ::1 is refused with 403 FORBIDDEN unless it carries an X-Demo-Key header matching the DEMO_KEY environment variable. That check runs before the action lookup, so an unauthorised caller gets 403 whether or not the action exists. An endpoint that can default a loan should not be reachable from venue wifi in a room full of hackers.
