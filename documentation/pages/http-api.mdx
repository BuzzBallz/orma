Orma exposes eleven `GET` routes over plain HTTP. The server is `src/api.mjs`: `node:http`, no
framework, no middleware stack. The default listen address is `http://localhost:8787`, overridable
with `PORT`.

Every response body on this page was captured from the running service against XRPL Devnet on
2026-09-12, server build `3.4.0-rc5`. All of them were taken at ledger `5263343` except the
`/api/demo/state` capture, which is from ledger `5263439` a few minutes later. Responses are
trimmed for length where noted, never rewritten.

<Warning>
This runs on Devnet, not Mainnet. XLS-65 vaults and XLS-66 lending are not amended into Mainnet, so
there is no production deployment to point at. `network` is hard-coded to `"devnet"` in
`src/api.mjs`, and `health.source` reports where the data came from: `"devnet"` for live reads,
`"fixtures"` for the recorded ring.
</Warning>

## Rules that bind every response

These are contract-level, not per-route. They are what makes the responses safe to consume.

### 1. Money is a decimal string in drops

One XRP is $10^{6}$ drops. Every monetary quantity leaves the API as a plain decimal string of
drops, never a JSON number.

XRPL `NUMBER` fields carry up to 19 significant digits and may arrive in scientific notation. A
JSON parse into a JS `number` destroys them silently, and `BigInt("1e17")` throws outright.

```js
// wrong, both of these
const nav = Number(body.navCorrect)
const assets = parseFloat(body.assetsTotal)

// right
import Decimal from 'decimal.js'
Decimal.set({ precision: 40 })
const assets = new Decimal(body.assetsTotal)   // "51000000" drops
```

Internally every amount is a `Decimal` at precision 40, and every serialisation goes through
`str()` in `src/num.mjs`, which emits `toFixed()` and therefore never scientific notation. A real
captured value that breaks a float: `"periodicPayment": "3333346.017258355048"`.

For chart pixel positions, `Number(x)` after dividing to a human scale is acceptable. For anything
displayed as a figure, it is not.

### 2. Absent means zero, and the API normalises it away

rippled omits any field whose value equals the type default. A vault carrying no unrealised loss
has **no `LossUnrealized` key at all**, not `"0"`. That single behaviour is the root of the finding
this whole project is built on, and it is handled in exactly one place: `num()` in `src/num.mjs`,
which maps `undefined`, `null` and `""` to zero.

Consumers may rely on presence. Every numeric field in every response below is always emitted,
defaulting to `"0"`.

<Note>
Two deliberate exceptions, both of which use `null` to mean "not known" rather than "zero".

On `broker-history`, `debtBefore`, `debtAfter`, `coverBefore` and `coverAfter` are `null`, not
`"0"`, when `brokerStateKnown` is `false`. An impairment does not touch the `LoanBroker` object at
all, so that transaction genuinely does not report the book. Emitting `"0"` would read as an empty
book, which is a different and much worse claim.

On the `pledge` block of `/api/mpt/:mptId/nav` and `/api/mpt/:mptId/resolve`, `valueHeld`,
`valueReported` and `overstatement` are `null` when the resolved document carries no `unitValue`,
alongside an `unpriced` explanation. Same reasoning: an unvaluable pledge is not a pledge worth
zero.
</Note>

### 3. Every 200 carries a ledger stamp

`serverTime` and `ledgerIndex` are prepended to every successful body by `stamp()`. `GET /api/health`
is the one body that does not go through `stamp()`, because it builds the same two fields itself.
`serverTime` is the **ledger close time** converted from the Ripple epoch (offset `946684800`), not
the server's wall clock, so two fields read in the same response come from the same ledger.

### 4. The default list order is worst first, by grade

`GET /api/vaults` sorts by `gradeNumeric` **ascending**. It does **not** sort by
`navDivergenceBps`.

$$\delta = \operatorname{round}\left( 10^{4}\cdot\frac{\text{NAV}_{\text{naive}} - \text{NAV}_{\text{held}}}{\text{NAV}_{\text{naive}}}\right)$$

Rounded to the nearest basis point, not truncated: `bps()` in `src/num.mjs` ends in `toFixed(0)`,
which is half-up under `decimal.js`. The captured divergence of `1961` is $1960.7843\ldots$ rounded,
and truncation would report `1960`.

Divergence only becomes non-zero once a loss has been **declared**. A manager sitting on an overdue
book who has declared nothing reports $L = 0$, so $\delta = 0$, so a divergence sort puts the most
dangerous facility at the bottom of the list. In the live capture below, `Kestrel Bridge Financing
II` sorts first at `gradeNumeric: 26` with `navDivergenceBps: 0`, above `Meridian Trade Finance I`
at `gradeNumeric: 89` with `navDivergenceBps: 1961`. That inversion is the thesis, not a sorting
bug: Meridian declared its loss and holds cash against every remaining claim, Kestrel has two
distressed loans and reports par.

### 5. Errors

```json
{
  "error": {
    "code": "VAULT_NOT_FOUND",
    "message": "No vault with that id",
    "retryable": false
  }
}
```

| code | status | retryable | raised when |
|---|---|---|---|
| `VAULT_NOT_FOUND` | 404 | false | the id is well formed but no snapshot exists for it |
| `NO_SHARE_MPT` | 404 | false | the vault has no share issuance, so there is nothing to value |
| `NO_BROKER` | 404 | false | the vault has no `LoanBroker`, so there is no conduct to reconstruct |
| `SHARE_NOT_TRACKED` | 404 | false | no facility on this service issues that MPT |
| `NOT_FOUND` | 404 | false | no route matched, or the demo capture file is missing |
| `FORBIDDEN` | 403 | false | an operator `POST` from something other than loopback |
| `INTERNAL` | 500 | true | anything unhandled |

A vault id must match `[A-Fa-f0-9]{64}` and an MPT issuance id `[A-Fa-f0-9]{48}`. Lowercase hex is
accepted and upper-cased before lookup. A path that matches no pattern returns
`{"error":{"code":"NOT_FOUND","message":"No route GET /api/nope","retryable":false}}`.

### 6. CORS, and which two routes are deliberately public

Every response carries `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Headers: *` and
`Access-Control-Allow-Methods: GET,POST,OPTIONS`, set unconditionally at the top of the request
handler so the local demo frontend works from any origin. `OPTIONS` returns `204`.

The meaningful distinction is caching, and it is opt-in per route. The default is
`Cache-Control: no-store`. Three routes pass `{ cors: true }` and get `Cache-Control: public,
max-age=4` instead:

- `GET /api/vaults/:vaultId/nav`
- `GET /api/mpt/:mptId/nav`
- `GET /api/mpt/:mptId/resolve`

The first two exist to be called by a party with no relationship to us. That is the entire point of
writing a URL into a token: a second broker handed vault shares as collateral holds an MPT issuance
id and nothing else, has no access to the facility's reporting, and has no reason to ask us for
permission first. Both serve read-only public ledger state, so there is nothing to protect, and
`max-age=4` matches `POLL_MS`, the reader's 4000 ms poll interval in `src/poll.mjs`, so a cache
cannot serve a figure older than one reader tick. `GET /api/mpt/:mptId/resolve` carries the flag as
well, because it is the diagnostic a lender runs against those same two routes.

<Warning>
The metadata that carries the NAV URL is written into the `MPTokenIssuance` at creation and can
never be rewritten. The contract at the end of those two routes is therefore effectively permanent:
fields may be added, nothing may ever be renamed, retyped or removed.
</Warning>

## Route index

| method and path | answers |
|---|---|
| `GET /api/health` | is the reader connected, and how old is the data |
| `GET /api/vaults` | which facilities are tracked, worst first |
| `GET /api/vaults/:vaultId` | everything about one facility |
| `GET /api/vaults/:vaultId/nav` | what is one unit actually worth |
| `GET /api/vaults/:vaultId/gate` | is this facility gated, and by whom |

| `GET /api/vaults/:vaultId/broker-history` | what did this manager actually do |
| `GET /api/mpt/:mptId/nav` | the same valuation, keyed by the token |

| `GET /api/indexer-race` | proof the first impairment is invisible to metadata diffing |
| `GET /api/demo/state` | which facilities are baked and live |

## GET /api/health

Is the reader up, which ledger is it on, and is it currently degraded. No parameters.

`ok` is `false` until the first poll tick completes. The API starts listening before the reader
connects, which is honest rather than pretending to be ready.

```bash
curl -s http://localhost:8787/api/health
```

```json
{
  "ok": true,
  "contractVersion": "1.0.0",
  "source": "devnet",
  "network": "devnet",
  "ledgerIndex": 5263343,
  "serverTime": "2026-09-12T22:20:22Z",
  "buildVersion": "3.4.0-rc5"
}
```

Two fields appear only while upstream is unhappy: `degraded: true` and
`lastLedgerAgeSeconds: <number>`. They are additive, and `source` never flips automatically. On a
failed read the reader keeps the last good snapshot rather than blanking, so a consumer should show
stale data with an age banner rather than an empty screen.

`buildVersion` is reported, never asserted. Devnet moves.

Things in there that are easy to misread:

- `oracle.dimensionsOnChain[].raw` is **hexadecimal**, because `AssetPrice` on an XLS-47 `PriceData`
  is a `UInt64` serialised as hex. `c4452` is 803922, which at `scale: 6` decodes to `0.803922`.
  Writing `"100"` into that field means 256, not one hundred. Full detail in
  [/mathematics](/mathematics#8-publication-as-an-oracle-object).
- `coverRateMinimum` and `coverRateLiquidation` are in units of $10^{-5}$. A stated `10000` is
  $0.10$. **Both** are divided by $10^{5}$, which is why `maxLiquidatableNow` is
  $\lceil 10{,}000{,}000 \times 0.10 \times 0.10 \rceil = 100{,}000$ drops against a
  `coverAvailable` of `"5000000"`. `strandedCoverFraction: "0.9800"` is the 98% of posted cover that
  cannot be reached at the current book size.
- `canWithdraw: false` with `withdrawBlockedReason: "tecTOO_SOON"` is **not an error**.
  `VaultWithdraw` returns `tecTOO_SOON` for the entire Investment phase of a closed-ended vault
  regardless of liquidity. It is a phase predicate, verified on Devnet with 80 XRP of
  `AssetsAvailable` sitting in the vault.
- `impairable: false` on an already-impaired loan is correct. A loan may only be impaired once it is
  already past due, and only once.
- `score.notchTrace` is the entire derivation. No weights are applied anywhere. See
  [/mathematics](/mathematics#5-composite-grade-by-ordinal-notching).
- `score.dimensions` carries **six** entries, not five. The sixth, `HEADLINE`, is the composite
  itself restated as a row so a table can render it alongside the factors. It is an output, not a
  measured factor.

Both readings are returned on purpose:

$$\text{NAV}_{\text{naive}} = \frac{A}{S} \qquad \text{NAV}_{\text{held}} = \frac{A - L}{S}$$

Handing over only the honest number asks the consumer to take our word for it. Handing over both,
with the gap named in basis points, lets them see what the obvious computation would have told them.
`provenance` names the three ledger fields so they can recompute it without trusting us:
$(51{,}000{,}000 - 10{,}000{,}000) / 51{,}000{,}000 = 0.803922$.

`assessment` is labelled `advisory: true` and can be `null`. The valuation is a measurement, the
grade is an opinion, and the grade failing to compute must never take the valuation down with it.

  "acceptedCredentials": [],
  "domainOwner": null,
  "note": "open to any depositor",
  "issuerNamed": false,
  "raterAddress": "rKQjjU5KFs9RAZCDvYVjcaoVK5gGsCJgkP"

<Warning>
`DomainID` is **not** stored on the `Vault` ledger entry. It lives on the share `MPTokenIssuance`.

## GET /api/vaults/:vaultId/collateral

What are the pledged shares of this facility actually worth. This is the route a second broker calls
before lending against a pledge.

| parameter | in | required | default | notes |
|---|---|---|---|---|
| `vaultId` | path | yes | | 64 hex characters |
| `accounts` | query | no | `WATCH_ACCOUNTS` plus the vault owner | comma separated addresses to scan for escrows. Added to the default set, not a replacement for it |
| `haircut` | query | no | `0` | the lender's own discount, in percent |

```bash
curl -s "http://localhost:8787/api/vaults/5763707D11EA19D1B5FF04E4EBA4F9336057955CDE65B725D1FF3EF2A96CB0E5/collateral?haircut=20"
```

```json
{
  "serverTime": "2026-09-12T22:20:22Z",
  "ledgerIndex": 5263343,
  "shareMptId": "000000014D667775372D5B78E07FFF294678C7F9CE82AFBC",
  "navNaive": "1.000000",
  "navCorrect": "0.803922",
  "pledgeCount": 0,
  "totalShares": "0",
  "totalValueNaive": "0",
  "totalValueCorrect": "0",
  "totalOverstatement": "0",
  "totalOverstatementPct": "0.00",
  "pledges": []
}
```

`haircut` is echoed per pledge as `haircutPct`, never at the top level, so this capture is byte for
byte the same with and without `?haircut=20`: no pledge was standing against Calder at that ledger.

Each element of `pledges`, when there are any, carries `escrowId`, `pledgor`, `beneficiary`,
`shares`, `valueNaive`, `valueCorrect`, `overstatement`, `overstatementPct`, `haircutPct`,
`maxLendable`, `finishAfter`, `cancelAfter` and `explorerUrl` (`presentCollateral` in
`src/collateral.mjs`).

The haircut applies to the **honest** value, never to the reported one:

$$V_{\text{lendable}} = u \cdot \text{NAV}_{\text{held}} \cdot (1 - h)$$

A haircut absorbs volatility. It does not absorb a misstatement. Marking a pledge at `valueNaive`
and then taking 20% off leaves a lender who believes they are 20% over-collateralised and is in fact
short.

<Note>
Vault shares are MPTs, and XLS-85 TokenEscrow accepts MPT amounts, so the pledge can sit on the
ledger where anyone can read it. Confirmed on Devnet: `EscrowCreate` with
`Amount: { mpt_issuance_id, value }` returns `tesSUCCESS`. What does not exist is a reverse index
from an `mpt_issuance_id` to the escrows holding it, so a lender has to be told which accounts to
scan. That is what `accounts` is for. An `Escrow` does appear in the owner directory of both the
pledgor and the beneficiary with the same object index, so a lender can enumerate pledges made in
their favour from their own account, and the API dedupes by escrow index so one pledge is not counted
once per account scanned. The missing global index is filed as developer feedback.
</Note>

This is the second lever, measured. Cover liquidated on one default is

$$T(p) = \min\Big(\big\lceil D \cdot c_{\min} \cdot c_{\text{liq}} \big\rceil,\; p,\; C\Big)$$

with $D$ the broker's **total** book, not the principal of the exposure that defaulted, and $D$
decremented as each default lands. Declaring the largest exposure first therefore consumes the least
first-loss capital. In this capture, 30 XRP first then 10 XRP consumed `"500000"` drops of cover.
10 XRP first then 30 XRP would have consumed `"700000"`. The 200,000 drop difference falls on the
unit holders, on identical losses.

`bestPossible` is best for depositors, meaning the most cover consumed. `worstPossible` is the
least. `fairness` is the observed consumption placed between them:

$$\phi = \frac{T_{\text{observed}} - T_{\min}}{T_{\max} - T_{\min}}$$

`"0.0000"` is the investor-worst sequence, `"1.0000"` the best, and it is defined as `"1.0000"` when
the two extremes coincide. `recommendation` is the same arithmetic pointed forwards, and is only
`applicable` with two or more distressed loans. Derivation in
[/mathematics](/mathematics#3-the-ordering-result).

<Note>

all, so a naive filter over `account_tx` silently drops every impairment. The join that closes it is
`Loan.FinalFields.LoanBrokerID` in the same transaction metadata. Before that fix every default
looked unsignalled, and the rule written to reward disclosure was penalising it.
</Note>

## GET /api/mpt/:mptId/nav

The same valuation as `/api/vaults/:vaultId/nav`, keyed by the share token instead of the vault,
because the issuance id is the only identifier a holder has. This is the route the token's own
metadata resolves to.

| parameter | in | required | notes |
|---|---|---|---|
| `mptId` | path | yes | 48 hex characters |
| `units` | query | no | value a specific pledge of N units |

Sends `Cache-Control: public, max-age=4`. Returns `SHARE_NOT_TRACKED` (404) if no tracked facility
issues that token.

```bash
curl -s "http://localhost:8787/api/mpt/000000014D667775372D5B78E07FFF294678C7F9CE82AFBC/nav?units=1000000"
```

The body is identical to `/api/vaults/:vaultId/nav` above, `schema: "orma.nav/1"`, plus one block
when `units` is given:

```json
{
  "pledge": {
    "units": "1000000",
    "valueHeld": "803922",
    "valueReported": "1000000",
    "overstatement": "196078"
  }
}
```

The `units` parameter exists so a lender does not have to reimplement decimal arithmetic to use the
figure. One million units against a held NAV of `0.803922` is worth `803922` drops. A tool reading
`AssetsTotal` alone marks the same pledge at `1000000`, an overstatement of `196078` drops, which is
19.61%.

This route never follows a metadata pointer itself. It is what a pointer points at, and a route that
followed one would be a loop.

as a success. And when a pledge cannot be valued, the `pledge` block is still returned with null
values plus an `unpriced` explanation, rather than crashing the caller. Both rules exist because an
early version of the pointer resolved to this diagnostic instead of to the valuation, returned a
perfectly good 200 with no `unitValue` on it, and took the caller down.
</Tip>

Following the pointer is bounded by a 2500 ms `AbortController` timeout. It is a URL written by a
third party, and it is the only step that leaves the ledger.

## Operator routes

There is one further family, `POST /api/demo/:action`, reserved for actions that mutate ledger
state during a live demo: impairing a loan, declaring a default, revoking a credential. It is not
part of the read API, and it is not documented per action because the action set is supplied by the
host rather than fixed by the server: `createApi(reader, { demo })` takes a map of action name to
handler, and `/api/demo/:action` dispatches into it.

<Note>
`src/index.mjs` does **not** pass a `demo` map. In the shipped entrypoint the dispatcher is reachable
but the map is empty, so every `POST /api/demo/:action` from loopback answers
`404 {"error":{"code":"NOT_FOUND","message":"no demo action \"<name>\""}}`. Nothing here mutates the
ledger as shipped. The facilities are built by the scripts in `src/demo/`, which are run from a
terminal and take no key. Treat this family as an extension point, not as an available API.
</Note>

It is bound to loopback. A request whose remote address is neither `127.0.0.1` nor `::1` is refused
with `403 FORBIDDEN` unless it carries an `X-Demo-Key` header matching the `DEMO_KEY` environment
variable. That check runs before the action lookup, so an unauthorised caller gets `403` whether or
not the action exists. An endpoint that can default a loan should not be reachable from venue wifi in
a room full of hackers.
